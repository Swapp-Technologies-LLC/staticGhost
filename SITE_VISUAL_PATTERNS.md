> **Scope:** Reusable section patterns for the marketing site (`index.html` at `staticghost.swapp.solutions`).
> **Companion to:** [`DESIGN_GUIDELINES.md`](DESIGN_GUIDELINES.md), which owns brand tokens, typography, and the anti-slop rules. This file owns *section-level patterns*: how a given kind of section is built, marked up, and captured.
> **Inherits without restating:** dark theme lock `#0b0f19`, accent `#00aced`, card surface `#111827`, border `#1f2937`, radius scale 12/8/pill, and the **zero em-dash rule** for all site copy.

## P-1 — Scrollytelling Product Tour

A sticky visual pane on one side, step text scrolling on the other. As each step scrolls through the viewport centre, the pane swaps to that step's screenshot.

**One per site.** A second scrollytelling tour anywhere on the site is a defect, not a feature. If another flow needs explaining, it gets a different pattern.

### Structure

Progressive enhancement, not graceful degradation. The no-JS state is the *authored* state; JavaScript upgrades it.

```html
<section class="tour" id="how-it-works" aria-labelledby="tour-heading">
  <h2 id="tour-heading">How it works</h2>

  <!-- Sticky pane: JS-only, decorative duplicate. Empty in the no-JS state. -->
  <div class="tour-pane" aria-hidden="true" data-tour-pane></div>

  <ol class="tour-steps">
    <li class="tour-step" data-tour-step="1">
      <h3>Create a project</h3>
      <p>One profile per blog, with its own container, port, and output folder.</p>
      <!-- Carries the accessible name. Visually hidden once JS activates. -->
      <img class="tour-step-img" src="assets/screens/step-1.png"
           alt="StaticGhost showing a new project profile with its port and output folder set."
           width="1440" height="900" loading="lazy" decoding="async">
    </li>
    <!-- steps 2..n -->
  </ol>
</section>
```

### Behaviour rules

1. **No JS:** every step renders its own image inline, stacked in reading order. The page is fully usable. This is the fallback and it requires no `<noscript>`.
2. **With JS:** the script sets `document.documentElement.classList.add('js-tour')`. CSS then reveals `.tour-pane`, makes it `position: sticky`, and visually hides the inline images with a clip-based utility that **keeps them in the accessibility tree**. Do not use `display:none` on them, or the alt text is lost.
3. **Swapping:** an `IntersectionObserver` with `rootMargin: '-45% 0px -45% 0px'` fires when a step crosses the viewport centre band. The observer sets the pane's image. Only one step is active at a time.
4. **Never** drive this with a `scroll` event handler.
5. **Below 900px:** the sticky pane is disabled entirely and the layout reverts to the stacked no-JS presentation. Sticky panes on small screens eat the viewport.
6. **`prefers-reduced-motion: reduce`:** no cross-fade between images. Swap instantly. The pane still swaps, because the swap is information, not decoration. Per `DESIGN_GUIDELINES.md` `MOTION_INTENSITY: 6`, the cross-fade elsewhere is fine; here it is suppressed.
7. **Preload** step 1's image eagerly (`loading="eager"`, `fetchpriority="high"`). Lazy-load the rest.

### Accessibility floor

- Each step is a real heading inside an ordered list. The tour reads correctly as a document with JS off or on.
- The sticky pane is `aria-hidden="true"` always. It is a visual echo of content already in the DOM.
- Alt text describes **the screen state**, not the step title. "StaticGhost showing a new project profile with its port and output folder set" beats "Step 1 screenshot".
- Do not trap focus or hijack scroll. No scroll-jacking, no `scroll-snap` on the tour container.

### Anti-patterns

- Auto-advancing the pane on a timer. The user drives it.
- Putting the tour above the fold. It sits below the hero, per hero discipline in `DESIGN_GUIDELINES.md`.
- Text in the screenshots that repeats the caption. The image shows, the caption tells.

## P-2 — Framed Product Screenshot

Every product screenshot on the site is generated by the capture script, never hand-taken. Hand-taken screenshots drift from the shipped UI, and a stale screenshot is a false claim about the product.

### Capture spec (all screenshots, no exceptions)

| Property | Value | Why |
| :--- | :--- | :--- |
| Viewport | `1440 x 900`, `deviceScaleFactor: 2` | Fixed so frames never jitter between runs. 2x for retina. |
| Output | `assets/screens/step-<n>.png` | Predictable, diffable paths. |
| Colour scheme | Dark, forced | Theme lock. Never capture a light-mode frame. |
| Chrome | Uniform app frame added in post | Consistency across Electron and browser captures. |
| Cursor | Hidden unless the step is about a click | Stray cursors read as sloppy. |
| Animations | Disabled during capture | Removes the main source of pixel diff noise. |

### Frame treatment

The Electron app and the published blog are two different surfaces. A shared frame is what makes them read as one story:

- 12px corner radius, matching the card radius.
- 1px border `#1f2937`.
- Soft shadow, no glow. Reserve cyan glow for Pro surfaces per the tier rules.
- Background inset `#0b0f19` so frames sit on the page ground without a seam.
- **Identical treatment for both surfaces.** Do not put macOS traffic lights on one and a browser bar on the other.

### Drift protection

The capture script is the single source of truth. A screenshot committed without a corresponding capture run is a bug. See milestone **M-T3** for the CI check that enforces this.

## P-3 — Step Caption Voice

Captions appear in three places and **must be identical in all three**: the tour page, the video overlay, and the screenshot alt text intent. One wording, three surfaces.

### Rules

1. **One sentence.** Present tense. What the user does, or what the product just did.
2. **No em-dashes.** Non-negotiable, inherited from `DESIGN_GUIDELINES.md`. Use commas, colons, or a full stop.
3. **No metrics that are not on screen.** No speeds, counts, percentages, savings, or timings unless the screenshot itself shows them and a benchmark file substantiates them. This rule exists because unsubstantiated performance claims are a live compliance issue for this project; see `private-docs/LEGAL_COMPLIANCE_SWEEP.md` L-21.
4. **No superlatives or absolutes.** No "instantly", "flawlessly", "100%", "zero downtime".
5. **Name real UI.** If the caption says "click Export", a control labelled Export must be visible.

### Demo data honesty

The tour is seeded with an obviously fictional demo blog. That is legitimate. What is not legitimate is anything that implies traction the product does not have.

| Allowed | Not allowed |
| :--- | :--- |
| A fictional demo brand, clearly invented | A real company's name or logo |
| Posts written for the demo | Fabricated view counts, subscriber counts, revenue |
| An empty or near-empty analytics view | A populated dashboard implying real usage |
| Real build output from a real run | Edited timings or hand-tuned logs |

Pick a demo brand that is unmistakably fictional and unlikely to collide with a real trademark. Verify the name is not an existing company before it goes into an asset that is expensive to regenerate.

## Asset layout

```
assets/
  screens/
    step-1.png ... step-n.png     generated, committed
  tour/
    seed/                         Ghost volume fixture + demo content
scripts/
  capture-tour.mjs                the only thing that writes assets/screens/
```

`npm run tour:capture` regenerates everything. Nothing else writes to `assets/screens/`.
